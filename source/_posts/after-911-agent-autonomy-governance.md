> 免责声明：这篇文章是主观推演，不构成建议。它写给“未来会发生什么”这个问题，而不是写给“应该怎么做”。

如果把 911 当作一个“拐点模板”，它给我们的启发并不是“某个行业太危险就会被终结”，恰恰相反：**当一种工具足够有用，社会更倾向于把风险治理成制度，而不是把工具扔掉。**

把这个模板套到 AI/Agent 上，一个最常见的担心是：

> 为了安全，未来会不会变成：AI 只能给建议，所有执行动作都必须人类审批？

听起来合理，但我认为这个结论过于简单。

原因很现实：如果每一步都要人类点确认，效率会被打回去，便利难以成立；而便利一旦不成立，系统就会倾向于“绕开规则”。

更重要的是，今天我们已经能看到另一条路线的雏形：

- Agent 负责执行
- 另一个 Agent 负责评估/复核
- 多轮迭代后再输出最终结果

这是一种把“审查”自动化的尝试。

因此，我更愿意把未来描述成一种折中：

- **低风险动作会越来越自动化**（甚至全自动）
- **高风险动作仍会被拦截**，但拦截方式不一定是“每一步人类审批”，而更像：权限边界、预算限额、审计追责、异常熔断等一整套“安全税”

下面我想把这套折中讲清楚：它为什么更可能发生，以及它会长成什么样。

## 1）先把问题说“像问题”：便利、权限、伤害半径

讨论 Agent 的安全，很容易陷入一种空泛：大家都知道有风险，但不知道风险到底在哪里。

我更喜欢把它拆成三个变量：

- **便利**：Agent 帮你省下多少时间/认知/操作成本
- **权限**：Agent 能触碰哪些资源（文件、账号、资金、对外发布、生产环境）
- **伤害半径**：一次错误能造成多大损失、影响多少人、是否可逆

你可以把“从建议到执行”的演化，看成是权限的不断扩张，而风险的陡升，往往来自伤害半径的突然放大。

一个非常贴近现实的推演路径是：

1. **建议阶段（低权限）**：只读、只写草稿、只输出文本。风险主要是误导，但可逆。
2. **高质量建议阶段（仍低权限）**：建议越来越有用，但本质仍是“人执行”。风险可控。
3. **执行阶段（权限跃迁）**：开始能发消息、改代码、调用 API、操作账号。便利明显，但风险急剧上升。
4. **制度化阶段（治理上桌）**：当事故累积到足够显眼，治理体系从“可选功能”变成“不可绕过的基础设施”。

这条线的残酷之处在于：大多数治理不是从“想清楚”开始的，而是从“被打疼”开始的。

但这里我想强调一个常被忽略的点：

> 安全不是 0/1。它更像一个从“聊胜于无”到“不可绕过”的连续谱。

所以即使在制度化之前，安全工作也并非毫无意义——它可能阻止不了第一次事故，但能降低事故频率、缩小伤害半径、减少不可逆后果。

## 2）“必须人类审批才能执行”这个命题，我认为太硬了

我上一篇强调“关键动作强制二次确认”，确实容易让人理解成：

- 所有执行都得人类点一下

这在很多场景下不现实。

因为你说得对：

- 如果一个 Agent 每执行一步都要人点确认，它会变成“更麻烦的搜索框”
- 人类的注意力是最稀缺的资源，越稀缺越会被绕过

但注意：**否定“处处审批”不等于否定“治理”**。

我认为更接近现实的治理形态是：

### 2.1 风险分层（不是“能/不能”而是“在哪个边界内能”）

Agent 不是要么自由，要么被锁死。

它会被允许在一个“政策信封（policy envelope）”里自主行动：

- 允许做：读信息、整理、总结、生成草稿、跑单元测试、开临时沙箱
- 条件允许做：发消息/提交 PR（在速率限制与权限范围内）
- 严格限制：转账、对外发布、删除数据、修改生产配置

**人类审批会收缩到“高风险边界的跨越时刻”。**

### 2.2 预算与限额（把灾难变成可控的损失）

真正决定事故是否“911 级”的，往往不是错误本身，而是错误的杠杆：

- 一次错，能造成 10 元损失，还是 1000 万损失？
- 一次错，能影响 1 个人，还是 1 亿人？

所以未来很多系统会默认内置：

- 金额限额（daily spend cap）
- 影响范围限额（rate limit / blast radius）
- 权限时效（短期 token / 任务级权限）
- 自动熔断（异常行为自动暂停）

你会发现，这些比“人类逐步审批”更有效率，也更工程化。

### 2.3 可审计与可追责（让人类不盯着也不意味着没人负责）

“AI 审 AI”这条链条可以降低错误率，但它不能解决责任问题。

监管真正要的是：

- 发生事故后，能不能解释发生了什么
- 能不能定位到责任主体（操作者/平台/提供方/部署方）

所以审计日志会越来越像航空黑匣子、像金融交易流水。

**你可以不让人类实时盯着，但你不能让系统变成“无人可问责”。**

## 3）多 Agent 不是“免审批”，它更像“把审批自动化”

你提到的现象很关键：

- 一个 Agent 做事，另一个 Agent 评估，多个回合迭代，最后产出结果

这确实像一种“自动化的审查”。

但我认为它不会取代治理，原因是：

- 它解决的是“质量问题”（做得对不对、好不好）
- 它不天然解决“授权问题”（凭什么它能做、它能做到哪一步）

换句话说，多 Agent 能替代的是“同行评审”，而不是“机场安检”。

同行评审可以让飞机设计更可靠，但机场安检决定你能不能把危险带上飞机。

## 4）我更担心的不是“会不会审批”，而是“会不会出现一场慢 911”

你预测第 4 阶段需要一次 911 级事件，我觉得非常可能。

但我想补一个更阴暗、更现实的可能性：

> AI 领域的“911”可能不是一次爆炸式事件，而是一种长期、低噪声、可否认的系统性伤害。

比如：

- 大规模诈骗与社会信任塌陷（不是一天发生，而是半年到几年）
- 大规模隐私泄露与勒索产业化
- 关键基础设施被自动化攻击链持续探测

这种“慢 911”更难让公众在某个瞬间愤怒到极点，但它会让监管像温水煮青蛙一样逐步收紧——最终同样把行业推向正规化。

## 5）一个具体例子：为什么“收紧权限”反而可能让 Agent 变得更强

很多人直觉上会觉得：权限越少，Agent 越没用；限制越多，发展越慢。

这个直觉在“玩具阶段”往往成立。

但一旦进入“要让更多人、更多组织长期使用”的阶段，情况会反过来：**可控性本身是一种能力**。

想象一个最简单的企业场景：

- 允许 Agent 读取邮件并起草回复（低风险）
- 允许 Agent 自动发送邮件给外部（中风险）
- 允许 Agent 自动给所有客户群发邮件（高风险）

如果没有权限边界、没有速率限制、没有审计日志，那么“最方便”的设计会直接变成“不可上线”的设计。

结果不是“更快发展”，而是：

- 只能少数极客自己玩
- 进不了关键业务
- 进不了金融/医疗/政务
- 一旦出事，组织会一刀切禁用

相反，如果系统从一开始就把权限做成可配置、可审计、可熔断：

- 组织敢让它接触更真实、更高价值的数据
- 敢把它接入更关键的流程
- 敢投入更多资源去训练、评估、迭代

这时的“限制”不是枷锁，而是进入更大舞台的门票。

所以我对未来的判断仍然是：

> 自主执行会越来越普遍，但它会被关进“权限、预算、审计、熔断”的笼子里。

你不一定需要每一步都人类点确认，但你一定需要一种机制，把不可控的自由变成可计算的成本。

## 结语

你提出的四阶段叙事，我基本认同。

但我会把结论写得更像工程现实：

- 未来不会是“AI 只能建议”
- 也不会是“AI 想干嘛就干嘛”

它会是一个更像航空、也更像金融系统的世界：

- **大部分操作自动化**
- **少数高风险操作被制度化拦截**
- **事故一定会发生，但伤害半径会被设计成可控**

如果真要押注，我押注的不是“审批是否存在”，而是：

> 监管会把“不可控的自由”变成“可计算的成本”。
